### Prototype

**You own the decision, not the code. The prototype is a throwaway instrument.**

Adapted from pstack's Prototype playbook. The one place where polish does not matter and speed does.

1. State the decision the prototype exists to make: which shell, which layout, which interaction, which density. No decision means no prototype: route to **create** or **screen**.
2. Gather references only if the space is open, and carry away conventions and counts, not looks (`references/ai-tells.md` §10b).
3. Build in a scratch folder, apart from production source: plain HTML and CSS, or the lightest thing that renders the idea. No framework, no abstractions, no tests.
4. Put the variants behind one switcher, buttons or a key, each labeled. Propose one the user did not ask for.
5. Use the same real content in every variant. A variant with nicer placeholder data wins unfairly.
6. Look at each one: capture every variant at the size that matters and drive the interaction.
7. Present the variants, the tradeoffs, and a recommendation. Hand the chosen direction to the playbook that builds it for real.

**Reply:** the decision, the variants, the evidence for each, tradeoffs, your recommendation, the scratch path. Say plainly that the prototype is throwaway.
